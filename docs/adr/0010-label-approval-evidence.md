# ADR-0010: 라벨로 표시한 사람의 승인을 기계가 받아 적는다

**상태:** 제안됨 — 이 ADR을 담은 Pull Request를 소유자가 병합하면 승인된 것으로 본다

**날짜:** 2026-11-10

## 맥락

공개 노트 한 편을 발행하려면 사람이 frontmatter에 승인 증적 일곱 필드를 손으로 적고,
산출물 세 개(`index.json`, `graph.json`, `glossary.json`)를 다시 만들어 커밋해야 한다.
이 일은 PC 앞에서만 할 수 있다. 판단에는 몇 분이 걸리지만 받아 적는 데 드는 수고가
더 커서, 2026년 10월 25일 이후 발행이 멈췄다.

판단과 기록은 다른 일이다. 헌장과 `public-content-review.md`가 사람에게 요구하는 것은
"재식별 가능성과 맥락을 읽고 결정하는 것"이지 "타임스탬프를 타이핑하는 것"이 아니다.
기록을 기계가 대신해도 사람의 결정이 명시적이고, 추적 가능하고, 되돌릴 수 있다면
"사람의 승인 없이는 아무것도 밖으로 나가지 않는다"는 원칙은 그대로다.

동시에 매일 초안을 준비하는 예약 에이전트(정원사, `docs/runbooks/garden-daily-agent.md`)가
생겼다. 헌장은 "AI 출력은 항상 `_AI_Staging`에서 시작한다"고 정했는데, 정원사는 공개
저장소의 draft Pull Request로 초안을 올린다. 이 관계도 여기서 정한다.

## 결정

### 1. 승인 행위

- 승인 행위는 **저장소 소유자가 Pull Request에 `approve` 라벨을 붙이는 것**이다.
- 라벨은 PR 본문의 "공개 노트 검토 체크" 여섯 항목이 모두 체크되어 있을 때만 효력이 있다.
  요구 항목의 단일 원천은 `docs/governance/public-content-review.md`의 Privacy Review
  체크리스트이며, PR 템플릿이 그것과 어긋나면 테스트가 실패한다.
- 라벨이 효력을 가지면 `.github/workflows/approval-evidence.yml`이
  `automation/apply_approval.py`를 실행해 PR이 바꾼 `draft`·`review` 노트에 증적을 적는다:
  `privacy_reviewed_by`와 `approved_by`는 라벨을 붙인 계정, 세 시각 필드는 기록 시각,
  `reviewed_revision`은 노트의 `updated`, `publish_state`는 `approved`.
- 워크플로는 이어서 산출물을 다시 만들고 기존 gate(검증기, `--check`, 테스트, grounding
  eval)를 그대로 돌린 뒤에만 PR 브랜치에 커밋한다. 하나라도 실패하면 아무것도 기록하지
  않고, 이유를 PR 댓글로 남기고, 라벨을 거둔다.
- **병합은 여전히 사람이 한다.** `published_at` 기록 방식은 이 ADR의 범위가 아니다.

### 2. 증적 무효화

- `approve` 라벨이 붙은 PR의 브랜치를 사람이 다시 고치면, 워크플로가 라벨을 거두고
  해당 노트의 증적을 지워 `draft`로 되돌린다. 이전 검토는 지금 내용을 본 것이 아니기 때문이다.
- 지금까지 이 규칙은 "수정하면 `updated`를 바꾼다"는 사람의 습관에 기대고 있었다.
  라벨 흐름 안에서는 기계가 강제한다.

### 3. 워크플로의 권한 경계

워크플로는 PR 브랜치에 쓸 수 있는 권한으로 실행된다. 공개 저장소에서 이것이 공격 경로가
되지 않도록 다음을 모두 만족할 때만 동작한다.

- 이벤트는 `pull_request_target`이다. 워크플로 정의는 항상 `main`의 것이어서 PR이 이 절차를
  바꿀 수 없다.
- 라벨을 붙인 계정이 저장소 소유자다.
- PR 브랜치가 fork가 아니라 이 저장소에 있다.
- PR이 바꾼 파일이 `vaults/CORCOIDUM-Public/**/*.md`와 `content/public/`의 세 산출물뿐이다.
  따라서 실행되는 스크립트는 전부 `main` 이력에 있던 것이다. 코드나 워크플로를 함께 바꾸는
  PR에는 라벨이 동작하지 않으며, 그런 PR은 기존 수동 절차를 따른다.

### 4. 정원사 초안과 `_AI_Staging`

- 공개 경로에서는 **병합되지 않은 정원사 PR 브랜치(`garden/…`)를 AI staging 영역으로 본다.**
  에이전트는 `publish_state: draft`만 쓰고 증적 필드를 쓰지 않는다. 그 초안이 `main`에
  들어가는 경로는 사람의 병합뿐이고, 발행 대상이 되는 경로는 사람의 `approve` 라벨뿐이다.
- 사람이 PR 댓글로 쓴 답변에서 온 문장과 에이전트가 정리한 문장은 같은 초안에 섞인다.
  그래서 승인 전 검토는 "에이전트가 답변에 없는 것을 보태지 않았는가"를 포함한다.
- Core Vault의 `_AI_Staging/` 규칙은 그대로다. RAG 답변 등 다른 AI 산출물에는 이 예외가
  적용되지 않는다.

## 근거

- 승인의 주체, 시각, 대상 버전이 지금과 같은 필드에 같은 의미로 남는다. 달라지는 것은
  누가 타이핑하느냐뿐이고, 커밋 이력에는 기계가 받아 적었다는 사실이 남는다.
- 체크리스트 완료를 기계가 강제한다. 손으로 적던 때에는 체크리스트를 건너뛰고 증적만
  적는 것을 막을 장치가 없었다.
- 라벨은 GitHub 모바일 앱에서 붙일 수 있고, 누가 언제 붙였는지 PR 타임라인에 남는다.

## 결과와 한계

- 워크플로는 노트가 공개해도 안전한지 **판단하지 않는다.** 체크박스가 체크되었는지만
  본다. 읽지 않고 체크하는 것은 막지 못한다. 그 책임은 지금처럼 사람에게 있다.
- 워크플로가 남긴 증적 커밋은 `GITHUB_TOKEN`으로 push되므로 PR의 `Public content gate`를
  다시 일으키지 않는다. 같은 검사를 워크플로가 push 전에 직접 돌리고, 병합 뒤에는
  `Deploy CCDOS Worker`가 배포 전에 한 번 더 돌린다.
- 승인 뒤 `main`을 PR 브랜치에 합치는 것("Update branch")도 사람의 수정으로 보고 증적을
  지운다. 보수적인 쪽을 택했다. 다시 읽고 라벨을 붙이면 된다.
- 1인 운영이므로 검토자와 승인자가 같은 계정이다. 기존 규칙과 같고, 두 역할의 시각은
  같은 값으로 기록된다.
- 라벨 없이 손으로 증적을 적는 기존 절차는 그대로 유효하다. 자동화가 멈추면 그쪽으로
  돌아간다.

## 검증

- `tests/test_apply_approval.py`: 체크리스트 미완료·인터뷰 PR·승인 대상 없음·검증기 실패 시
  아무것도 쓰지 않음, 기록한 증적이 검증기를 통과함, 무효화가 원래 draft를 그대로 복원함,
  템플릿·README·Vault 밖 경로를 건드리지 않음, PR 템플릿과 거버넌스 체크리스트의 일치.
- 워크플로 자체는 `pull_request_target`의 성격상 `main`에 병합된 뒤에만 실행된다. 병합 후
  합성 노트 PR로 승인·거부·무효화 세 경로를 한 번씩 확인하고 그 PR은 병합하지 않고 닫는다.
